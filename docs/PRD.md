# PRD: SQL Server CDC Data Extractor (.NET Windows Service + Windows App)

## 1. Контекст и проблема
Нужен экстрактор данных из Microsoft SQL Server, который работает на Windows Server как сервис и запускается по расписанию. Конфигурация и управление выполняются через Windows-приложение (installer + первичный конфигуратор + менеджер статусов). При первом подключении для набора таблиц экстрактор:
1) настраивает CDC (Change Data Capture) для выбранных таблиц;
2) выполняет первичную полную выгрузку данных (опционально с ограничениями по дате/периоду).

При каждом последующем запуске он:
1) выгружает только дельты через CDC (изменения с момента последнего успешного запуска);
2) управляет retention/cleanup CDC в SQL Server (см. раздел 6.4).

Примечание по планированию работ: реализация разбита на фазы, см. `PHASES.md`.

## 2. Цели (Goals)
1) Автоматическая первичная и инкрементальная выгрузка данных из SQL Server для набора таблиц.
2) Надежное возобновление после сбоев без “дыр” и по возможности без дублей.
3) Минимальные операционные усилия: .NET Windows Service + Windows App, конфиг, логирование, метрики, алерты.
4) Управляемая “история”: CDC retention/cleanup на стороне SQL Server.

## 3. Не цели (Non-goals)
1) Реализация полноценного CDC-коннектора уровня Kafka Connect (распределенный, горизонтально масштабируемый).
2) Трансформации данных (ETL) сложнее нормализации типов и (опционально) маппинга имен колонок.
3) Изменение схемы исходной БД (кроме требуемого для CDC и минимально необходимых прав/ролей).

## 4. Пользователи и стейкхолдеры
1) Data engineer / BI engineer: настраивает таблицы, расписание, целевое хранилище, наблюдаемость.
2) DBA (если есть): контролирует права, нагрузку, retention/cleanup CDC, изменения на сервере.
3) Система-потребитель (DWH/озеро/ETL): получает полные данные и/или поток изменений.
4) Администратор клиента без DBA: ожидает “self-serve” настройку и безопасные значения по умолчанию.

## 5. Основные сценарии (User stories)
1) Как data engineer, я задаю список таблиц и расписание, и сервис сам включает CDC и делает первичную выгрузку.
2) Как data engineer, я хочу чтобы последующие запуски выгружали только изменения с момента последнего успешного запуска.
3) Как DBA, я хочу контролировать retention CDC и видеть, что сервис не “забивает” change tables и лог.
4) Как оператор, я хочу видеть в логах/метриках прогресс (таблица, LSN, строки), ошибки и время выполнения.

## 6. Требования

### 6.1 Функциональные требования

**FR-01. Режим работы**
Сервис работает как **Windows Service** (долгоживущий процесс), который выполняет задания по расписанию и по командам из Windows-приложения (менеджера).
Отдельного “`run-once` консольного процесса” в MVP нет: разовые прогоны, получение онлайн-логов и диагностика выполняются через менеджер, подключенный к сервису по IPC.

**FR-01a. IPC между менеджером и сервисом**
Windows-приложение (менеджер) должно иметь **двустороннее подключение** к сервису через локальный IPC (MVP: Windows Named Pipes; протокол: любой, например gRPC/JSON-RPC).
Через IPC менеджер должен уметь:
1) получать статус сервиса и прогонов (включая прогресс по таблицам);
2) запускать “прогон сейчас” (manual trigger) и управлять очередью/блокировками;
3) получать онлайн-логи (стрим) и последние N строк;
4) получать диагностические проверки prerequisites (SQL Agent, права, CDC enablement) с понятными ошибками для пользователя.

Решение (MVP):
1) Транспорт: **Windows Named Pipes**.
2) Протокол: **JSON-RPC** поверх stream.
3) Библиотека: **StreamJsonRpc (Microsoft)**.
4) Стриминг логов: подписка/отписка (subscription) + notifications (server->client) по JSON-RPC.
5) Безопасность: ACL на pipe (доступ только для нужных учетных записей/групп).

**FR-02. Конфигурация**
Сервис читает конфиг из файла (например `config.yml`/`config.json`) + секреты из защищенного источника (Windows Credential Manager/DPAPI/ENV).
Конфиг задает:
1) подключение к SQL Server (host, instance, database, auth);
2) список таблиц (schema.table) и параметры по таблице;
3) интеграцию с downstream-сервисом по HTTP API (url, auth, лимиты/чанки);
4) формат выгрузки: CSV + schema manifest (JSON);
4) расписание;
5) параметры CDC/cleanup;
6) параметры ретраев/таймаутов/батчинга.

Примечание: подробный контракт HTTP API, включая безопасность, идемпотентность, лимиты MaxBytes и обработку ошибок, описывается в отдельном документе `APIs.md`.

**FR-03. Онбординг таблиц (первый запуск)**
Для каждой таблицы, выбранной в Windows UI и сохраненной в конфиг/state, сервис:
1) проверяет prerequisites для CDC на БД (включена ли CDC);
2) включает CDC на базе (если разрешено конфигом);
3) включает CDC на таблице (capture instance по стандарту или по конфигу);
4) выполняет первичную выгрузку данных:
   - Полная таблица, либо по “окну по дате” (см. FR-04);
   - В согласованной точке во времени (см. FR-05).
5) сохраняет состояние “последний обработанный LSN” (см. FR-09).

**FR-04. Ограничение первичной выгрузки по дате**
Для таблиц, где это применимо, поддержать ограничение первичной выгрузки:
1) `watermark_column`: имя колонки (datetime/date/int) по которой делается отбор;
2) `start` / `end` (или `start` + “выгружаем до текущего момента”).

Примечание: “произвольный WHERE из конфига” допускается только при строгой валидации, чтобы исключить SQL injection. Безопасный вариант: ограничиться whitelisted колонкой + параметризованными значениями.

**FR-05. Консистентность между snapshot и CDC**
Первичная выгрузка и точка старта CDC должны быть согласованы, чтобы изменения не потерялись:
1) Сервис фиксирует `start_lsn` перед/в момент snapshot (подход зависит от выбранной стратегии).
2) После snapshot дельты читаются начиная с нужного LSN, чтобы покрыть изменения “параллельно” snapshot.

Варианты стратегии (выбрать одну как MVP):
1) “Snapshot затем CDC”: сделать snapshot под `SNAPSHOT`/`READ COMMITTED SNAPSHOT` (если включено) и взять LSN так, чтобы последующий CDC догнал изменения после snapshot.
2) “LSN-границы”: получить `from_lsn`/`to_lsn` и выгрузить изменения в окне, затем snapshot.

**FR-06. Инкрементальная выгрузка (каждый следующий запуск)**
Для каждой таблицы:
1) загрузить сохраненный `last_processed_lsn` (см. FR-09);
2) вычислить `to_lsn` = “текущий верхний LSN”;
3) прочитать CDC изменения в диапазоне `(last_processed_lsn, to_lsn]` батчами;
4) выгрузить изменения в целевое хранилище;
5) после успешной записи продвинуть `last_processed_lsn = to_lsn`.

**FR-07. Семантика выгрузки: `changelog`**
MVP: выгружаем CDC события (insert/update/delete) как журнал изменений в downstream-сервис по HTTP API.

**FR-08. Дедупликация/идемпотентность**
Сервис должен быть безопасен к повторному запуску одного диапазона LSN:
1) В `changelog` режиме: уникальный ключ события (table + start_lsn + seqval + operation) или иной стабильный идентификатор.
2) На уровне чанков/порций: ключ `(table, from_lsn, to_lsn, chunk_no)` и идемпотентный `commit` для `(table, from_lsn, to_lsn)`.

**FR-09. Хранение состояния (state store)**
Сервис хранит состояние по таблицам минимум:
1) включена ли CDC на таблице/БД;
2) `last_processed_lsn` (и, при необходимости, доп. маркеры);
3) версия схемы/хэш колонок (для контроля изменений).

Варианты хранения (выбрать один как MVP):
1) локально на сервере: файл SQLite / JSON (предпочтительно SQLite);
2) в отдельной служебной БД (если нужен shared-state).

**FR-10. Параллелизм и батчинг**
1) Возможность обрабатывать таблицы параллельно с ограничением `max_parallel_tables`.
2) CDC чтение и запись в sink выполняются батчами (`batch_rows`, `batch_bytes`).
3) Ограничение нагрузки: `max_runtime`, `max_rows_per_run` (опционально).

**FR-11. Планировщик**
Запуск по расписанию:
1) Внутренний scheduler в сервисе (например cron-подобный) или интеграция с Windows Task Scheduler.
2) Защита от перекрывающихся запусков: “single instance lock”.
3) Расписание по умолчанию: 08:00, 12:00, 18:00 (локальное время сервера). Должно быть конфигурируемым.
4) Поддержка ручного запуска прогона через IPC (см. FR-01a) без остановки сервиса.

**FR-12. Обработка ошибок и ретраи**
1) Ретраи на transient ошибки (сеть, таймауты, deadlocks) с backoff.
2) Разделение ошибок по уровням: table-level (пропускаем таблицу) vs job-level (останавливаем весь прогон).
3) Отчет о статусе прогона (успешно/частично/ошибка).
4) Обнаружение “CDC gap”: если `last_processed_lsn` меньше минимального доступного LSN в CDC (история уже очищена), сервис должен:
   - явно зафиксировать ошибку состояния (не молча продолжать),
   - перевести таблицу в режим re-bootstrap (полный snapshot заново),
   - уведомить пользователя в UI с причиной и рекомендацией (частота прогонов/retention/SQL Agent).

**FR-13. Наблюдаемость**
1) Структурированные логи (JSON) с correlation id прогона, таблица, диапазон LSN, счетчики.
2) Метрики: длительность, строки, лаг (to_lsn - last_processed_lsn), ошибки, ретраи.
3) Health endpoints/Windows Event Log (минимум одно).
4) Менеджер должен уметь подписываться на поток логов сервиса через IPC (см. FR-01a).

### 6.2 Нефункциональные требования
**NFR-01. Совместимость**
1) Windows Server (версия уточняется).
2) SQL Server: 2016+ (уточнить минимальную версию, редакцию и требования CDC).

**NFR-02. Безопасность**
1) Принцип наименьших привилегий: отдельный login/user, права строго по нужным БД/таблицам + права на CDC.
2) Секреты не хранятся в открытом виде в конфиге.
3) Поддержка TLS (Encrypt=True) при подключении к SQL Server.

**NFR-03. Надежность**
1) “At-least-once” доставка в sink как базовая гарантия.
2) Непотеря данных при рестарте сервиса/сбое (state store + идемпотентность).

**NFR-04. Производительность**
1) Инкрементальная выгрузка должна завершаться в пределах окна расписания при разумных объемах изменений.
2) Должны быть настройки для ограничения нагрузки на SQL Server.

**NFR-05. Эксплуатация**
1) Простая установка/обновление (MSI/zip + service install).
2) Конфиг и state сохраняются при апдейте.
3) Ротация логов.

### 6.3 Требования к данным (схема, типы, ключи)
1) Корректная типизация (datetime2, decimal, nvarchar, uniqueidentifier, varbinary).
2) Обработка nullable.
3) Определение PK/unique key в schema manifest (авто-детект из метаданных).
4) Таблицы без PK/unique index:
   - если “small table” (порог задается конфигом): разрешить стратегию полного snapshot на каждом прогоне;
   - иначе: запретить подключение таблицы и показать причину в UI.

### 6.4 “Очистка истории” (cleanup) — что именно чистим
MVP: управляем retention/cleanup CDC в SQL Server, потому что у части клиентов может не быть DBA.
1) Проверить, что SQL Agent включен и запущен.
2) Проверить наличие CDC jobs для базы (capture/cleanup).
3) Настроить retention (по умолчанию 7 дней, конфигурируемо) и обеспечить, что частота прогонов не приводит к потере изменений из-за очистки.
4) Политика применения: не понижать retention, если на сервере уже выставлено больше; при меньшем значении поднять до минимального.
4) (Опционально) Триггерить cleanup job только если это безопасно и согласовано как продуктовая политика.

## 7. Высокоуровневая архитектура
Компоненты:
1) **Windows Service Host**: держит scheduler, lifecycle, health.
2) **Windows App**: installer + первичный конфигуратор (выбор таблиц) + менеджер статусов.
2) **Extractor**: логика snapshot + CDC delta.
3) **CDC Manager**: enable/verify CDC на БД и таблицах.
4) **State Store**: хранит LSN/статусы/схемы.
5) **Sink Writer**: HTTP клиент для downstream-сервиса (chunk upload + commit manifest).
6) **Observability**: логирование, метрики, алерты.
7) **IPC Layer**: Named Pipes endpoint в сервисе + клиент в Windows App (команды, статусы, стрим логов).

Поток данных:
1) Config -> Table Plan
2) (Первый запуск) Snapshot -> Sink -> State (LSN)
3) (Повторные) CDC Delta -> Sink -> State (advance LSN)
4) Cleanup (CDC retention / sink retention)

## 8. Интерфейсы и конфиг (черновик)
Пример структуры (псевдо):
1) `sql`: connection string / параметры
2) `schedule`: cron/interval, timezone
3) `tables[]`: schema, name, mode, watermark_column, start/end
4) `cdc`: auto_enable_db, auto_enable_table, retention, cleanup_policy
5) `sink`: type=http, base_url, auth, chunking (max_rows/max_bytes), commit_policy
6) `formats`: csv (служебные колонки), schema_manifest=json
6) `state`: type (sqlite), path

## 9. Ограничения и риски
1) CDC требует прав и может быть запрещен политикой DBA.
2) Таблицы без PK усложняют `replica` режим.
3) Большие таблицы: первичная выгрузка может быть тяжелой; нужна стратегия “чанки” по ключу/дате.
4) Retention CDC: если сервис не успевает, изменения могут быть очищены до чтения.
5) Изменения схемы (add/drop/alter columns): нужен план совместимости (версионирование схемы, fail-fast или auto-migrate).

## 10. Acceptance criteria (MVP)
1) Сервис на Windows поднимается и запускается по расписанию без пересечений прогонов.
2) Для заданных таблиц включает CDC (если разрешено) и делает первичную выгрузку.
3) На следующем прогоне выгружает изменения только из CDC, корректно продвигая LSN.
4) После падения на середине прогона при повторном запуске данные не теряются (допускаются дубли, если они идемпотентно обрабатываются).
5) Есть логи и метрики, позволяющие диагностировать отставание и ошибки.
6) Если сервис обнаруживает “CDC gap” из-за истекшего retention, он не продолжает инкрементально, а переводит таблицу в re-bootstrap и отражает это в UI.

## 11. Открытые вопросы (нужно ответить, чтобы “закрыть” PRD)
1) Точные эндпоинты HTTP API downstream-сервиса: `uploadChunk`, `commit`, `abort`, `status` (или иной контракт).
2) Лимиты HTTP: максимальный размер чанка/запроса, таймауты, ретраи, требования к идемпотентности.
3) Как маркировать initial snapshot в “changelog” (отдельный тип `_op`, отдельный dataset, или отдельный pipeline).
4) Порог “small table” для snapshot-fallback без уникального ключа (по умолчанию ~1000 строк, конфигурируемо).
5) Стратегия консистентности snapshot+CDC (выбрать один конкретный алгоритм для MVP).
6) Версии Windows Server/SQL Server и аутентификация (SQL login vs Windows/AD) как поддерживаемая матрица.
7) Политика маркировки/доставки re-bootstrap (snapshot) в downstream (см. `APIs.md`).
