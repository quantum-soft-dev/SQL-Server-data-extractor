# Фаза 3: Расширения и оптимизации

## Overview
Добавить функциональность поверх production-ядра: эволюция схемы, более гибкие сценарии re-bootstrap, оптимизации производительности, дополнительные политики и улучшения контракта с downstream.

## Цели
1) Упростить жизнь пользователю при ALTER TABLE и больших изменениях.
2) Сократить нагрузку на SQL Server и ускорить выгрузки.
3) Дать более гибкие режимы эксплуатации без усложнения MVP.

## Scope (входит)
1) Эволюция схемы:
   - детект изменения схемы (schema_hash) и автоматическая публикация новой schema версии;
   - управляемое поведение: “остановиться и попросить re-init” vs “авто re-bootstrap”.
2) Re-bootstrap UX:
   - re-init по одной таблице (если решим расширить сценарий);
   - управляемые миграции (подтверждение в UI перед SNAPSHOT).
3) Оптимизации:
   - тюнинг чтения CDC (batching, backpressure);
   - тюнинг snapshot для больших таблиц (chunking по ключу/дате, если добавим).
4) Small-table fallback:
   - конфигурируемые пороги (строки/размер);
   - отчет пользователю, почему таблица перешла в snapshot-only.
5) Расширение API:
   - детальные статусы dataset (progress);
   - более строгие commit manifests (expected_chunk_count и т.п.).

## Out of scope
1) Replica режим (если не будет отдельного бизнес-требования).
2) Поддержка других источников кроме SQL Server.

## Deliverables
1) Обновленные документы `PRD.md`, `APIs.md`, фазы.
2) Реализованные фичи из scope с тестовыми сценариями.

## Definition of Done / Acceptance
1) При изменении схемы система либо автоматически проходит re-bootstrap, либо явно и понятно требует действия в UI.
2) Большие таблицы выгружаются в приемлемые сроки без перегруза SQL Server (настраиваемые лимиты).
3) Downstream получает однозначный manifest и может детерминированно собирать файлы.
